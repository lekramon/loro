# Manual acquisition and download-client recovery

Label: ready-for-agent
State: done

## Sequence

1. Configure and test one qBittorrent 5.x WebUI connection (implemented).
2. Persist candidate observations, explicit selection/profile override confirmation and supported torrent identity before submission (implemented in ticket 02).
3. Persistent workers, submission intent, category/tags, duplicate exclusion and uncertain-response reconciliation (implemented in ticket 03).
4. Polling, completion/failure history and provisional handoff to import (implemented in ticket 04).

Tickets 01–04 have executable contracts. Import requires its own feature contract before implementation. Automatic acquisition, upgrades, series, remote access and import remain outside these slices.

## Ticket 01 requirements

- DCL-001: GET/PUT `/api/v1/download-client` reads/saves one qBittorrent connection. Unconfigured: configured=false, revision=0, empty url/username, hasPassword=false, appVersion/apiVersion/checkedAt=null. PUT requires completed onboarding, current revision, url and username; password may be omitted or blank to preserve an existing password only when endpoint and username are unchanged. Initial configuration and endpoint/username changes require a nonempty replacement. Never trim a password. Accept valid UTF-8 up to 1024 bytes, excluding NUL; whitespace may be meaningful. Password is write-only in private SQLite. Username is public configuration, trimmed, 1–100 Unicode characters without controls. URL is trimmed HTTP(S), up to 2048 bytes, valid host/port, no userinfo/query/fragment; strip trailing slashes and preserve a reverse-proxy base path. The client appends `/api/v2/...`. Save makes no network request, increments revision and clears successful test evidence; stale writes return 409.
- DCL-002: POST `/api/v1/download-client/test` requires the normal mutation header, JSON content type and exactly an empty object. Complete setup first. One test at a time, a ten-second operation budget, two-second HTTP attempts, no automatic retries and no redirects. Create a private cookie jar for this test; POST form-encoded username/password to auth/login with matching Origin/Referer. Require `Ok.` and a usable nonempty SID cookie. `Fails.` and HTTP 401/403 classify as authentication failure; do not repeat logins automatically. SID and credentials never enter public responses, browser storage or diagnostics. Fresh requests authenticate on every test; no session persists between tests or restarts. After obtaining a session, attempt logout with an independent one-second cleanup deadline even on failure/cancellation; remote cleanup is best effort, not proof that a timed-out server destroyed its session.
- DCL-003: Authenticated GET app/version and app/webapiVersion validate a stable `v5.<minor>.<patch>` (optional v prefix) and API `2.<minor>[.<patch>]`, numeric components at most six digits. Return 503 download-client-unsupported-version for syntactically valid unsupported versions; malformed, HTML, oversized (>4 KiB), missing session or unexpected login success responses return 502 download-client-invalid-response. Classify unavailable, timeout, authentication and rate-limit separately. 429 exposes Retry-After clamped to 1–3600 seconds and establishes a process-local cooldown scoped to configuration revision. No retry of a login, version request or logout; no torrent/category/tag/settings mutations. Test proves authentication and version readability, not submission permission, path mapping or transfer capability.
- DCL-004: Success persists appVersion/apiVersion/checkedAt only while configuration revision matches. Changing configuration during a test returns 409 download-client-changed without stale success. Failed tests preserve prior successful evidence and show a failure separately. Readiness depends on local storage, not client availability. Never include endpoint, password, cookie or raw upstream body in errors/logs. A stopped/restarted service preserves private configuration/evidence but not transient sessions or cooldowns.
- DCL-005: Additive migration 7 creates a separate download_client_configuration table. Preserve settings, catalog, inventory/associations, source configuration/capabilities and private TMDB credential files. Validate the new table at readiness. Prior binaries reject schema 7; rollback restores a matching pre-upgrade stopped-service backup, never destructive Down migration. Use existing serialized writes and short transactions; no network in transactions. No new runtime dependency or toolchain change.
- DCL-006: Settings shows a localized qBittorrent section with WebUI base URL, username, masked password, saved password presence, Save/Test/Reload and historical successful version/time. Clear typed secrets after save success or failure; never prefill/store passwords in browser state persistence. Disable Test for unsaved edits. Show classified errors, require reload on revision conflict and preserve shared header, theme/language geometry. Say that testing does not start downloads. Keep existing mock Downloads and Releases behavior unchanged.

## Ticket 02: durable selection and identity

- ACQ-001: Successful registered-movie search persists immutable candidate/profile/source observations and returns an opaque 32-hex observationId for each result. Keep the existing candidate ID and order. Observations expire after 30 minutes for new selection; clean expired unreferenced observations on later searches. Snapshot original language, movie title, source name/revision/endpoint, profile revision/full profile and all candidate explanations. Private references/claims never serialize publicly. Recheck source/settings revisions inside the observation transaction; failed persistence fails the search rather than returning unusable IDs. References are at most 8192 bytes. Prefer one unambiguous magneturl attribute, otherwise the enclosure/link. Ambiguous references or conflicting advertised infohash evidence remain explicit preparation-review reasons.
- ACQ-002: POST `/api/v1/acquisitions` accepts exactly observationId, idempotencyKey (16–80 ASCII letters/digits/underscore/hyphen) and confirmOverride (boolean). Require setup. New selection requires a live observation and matching current source/profile revisions. Mismatch or unknown profile status requires confirmOverride=true; matched candidates record overrideConfirmed=false. Never update preferences. Persist selection and immutable evidence before any retrieval. A request-key replay with identical observation/confirmation returns its original acquisition even after expiry/config changes; reuse with different input returns 409. Serialize selection; deduplicate active acquisitions by movie and candidate identity. Persist every accepted request key's association. Return 201 for new selection, 200 for replay/dedup, `{acquisition,created}`. New state is selected, revision=1; POST selection makes no external request.
- ACQ-003: GET `/api/v1/acquisitions?limit=25&offset=0&movieId=<optional>` and GET `/api/v1/acquisitions/<32-hex-id>` return public snapshots, state, revision, timestamps, override evidence and nullable v1 infoHash/kind/reviewCode. List limit 1–50, offset 0–10000, newest first. Never return provider GUIDs, URLs/magnets, tracker credentials or metainfo bytes. Reading history works offline and after restart.
- ACQ-004: POST `.../<id>/prepare` and `.../<id>/cancel` require exactly `{revision}` and global mutation protections. One in-process preparation at a time; claim selected/needs-review with revision compare-and-swap, persist preparing, increment revision before retrieval. A ready acquisition is already prepared; preparing/cancelled cannot be prepared. Cancellation is local and terminal, increments revision and fences any in-flight completion; it never removes files/torrents. An old revision returns 409. Cancelled records remain history, release active duplicate exclusion, and allow a fresh selection. User-visible states: selected, preparing, ready, needs-review, cancelled. Ticket 02 itself creates no download task or submission job; ticket 03 adds explicit submission and blocks local cancellation after enqueueing.
- ACQ-005: Preparation parses v1 btih magnets (40 hex or 32 base32, canonical lowercase hex); reject conflicting/absent hashes, malformed magnet query, btmh/v2/hybrid identity for this slice. Magnet parsing does not join peers, fetch metadata or contact trackers. Alternatively retrieve HTTP(S) metainfo only from the configured source's exact scheme/host/effective port, preserving path/query but rejecting userinfo/fragments and all redirects; do not append or forward saved API keys. Credential-bearing supplied references stay private. No arbitrary client-provided URLs. One four-second request, no retries, 4 MiB body limit and ten-second API deadline. Classify auth/rate-limit/timeout/unavailable without raw diagnostics; persist review rather than retry automatically. Preparation never calls qBittorrent.
- ACQ-006: Validate canonical bounded bencoding (depth 32, 100000 tokens, one complete top-level dictionary, unique sorted dictionary keys, canonical integers/string lengths). Validate v1 info/name/piece length/pieces and positive total length, either one length or a bounded multi-file list (10000 files, 64 UTF-8 path segments, safe nonempty path components and UTF-8 alternate names/paths; no traversal/separators/NUL/controls or symlink metadata). Piece length max 64 MiB; total at most JSON-safe integer 9007199254740991; piece hash count must cover total bytes. Reject v2/hybrid metadata for review. Compute SHA-1 from the exact original encoded info span, not re-encoding. Compare any normalized advertised hash against magnet/computed identity. Store exact metainfo bytes or private magnet/reference with ready intent for later submission; never download payload media. Torrent identity identifies content addressing, not movie identity or proof that its bytes already exist.
- ACQ-007: Complete preparation only with its current revision/state and unchanged source revision. Existing intent keeps its confirmed profile snapshot even if preferences change later. Source changes result in needs-review/source-changed; old credentials are never moved to a new endpoint. Read-only retrieval failures/unsupported identity leave needs-review with a fixed sanitized reviewCode. Explicit Retry identity preparation reuses that intent; cancel/research permits a new reference/profile observation. On startup, under the existing instance lock before traffic, recover preparing rows to needs-review/preparation-interrupted with incremented revision; never replay network work automatically. Selected/ready/review/cancelled survive restart unchanged. Pending cleanup is unnecessary because this slice creates no media files.
- ACQ-008: Additive migration 8 creates observations, acquisitions and idempotency request mappings with foreign keys and an active-dedup unique index. Preserve schema-7 configuration, catalog, inventory/associations, sources, client credentials and TMDB files. Ready validates new tables. Older binaries reject 8; rollback restores a matching stopped-service backup. Keep SQL transactions local/short, including revision fences, and fail startup on migration/recovery errors. No new dependency.
- ACQ-009: Releases offers Select release, showing movie/candidate/explanations in an accessible confirmation dialog. Explicit override checkbox is mandatory only for mismatching/unknown candidates; Cancel leaves no intent. Prepare acquisition creates the saved selection then explicitly requests preparation. Retain the request key for retry after uncertain selection response and refresh public history after uncertain preparation. A per-movie history panel shows saved states/hash/review reason, Refresh, Retry identity and Cancel acquisition with revision checks. All copy supports en-US/pt-BR and existing branding/themes/header/mobile layout. Clearly state identity preparation starts no downloads; don't add a nonfunctional Download button or change the mock Downloads screen.

Errors: strict/duplicate/null/unknown request fields 400, global Host/Origin/header/content-type/body errors unchanged; 422 validation-failed; 404 acquisition-not-found/observation-not-found; 409 observation-expired/observation-changed/profile-confirmation-required/idempotency-conflict/acquisition-changed/acquisition-state-conflict/preparation-in-progress/setup-required; 503 storage-unavailable/not-ready. Provider/retrieval errors are persisted reviewCode in a successful preparation response; database failure remains 503 and startup recovery handles an interrupted preparing row.

References: [BEP 3](https://www.bittorrent.org/beps/bep_0003.html), [BEP 9](https://www.bittorrent.org/beps/bep_0009.html), [BEP 52](https://www.bittorrent.org/beps/bep_0052.html). V1-only support, bounds, observation expiry, same-origin policy and review states are this application's implementation choices.

## Ticket 03: submission and reconciliation

These requirements extend ticket 02; identity preparation still starts no download. Only an explicit Submit to qBittorrent action authorizes transfer. Polling, completion/import, torrent removal and remote path translation are excluded.

- SUB-001: POST `/api/v1/acquisitions/{id}/submit` requires exactly `{revision,clientRevision,settingsRevision}` (positive integers). Require setup, a ready v1 acquisition, current acquisition/client/settings revisions, configured client and persisted download directory. Persist one version-1 submit job and immutable client revision/download-directory/settings-revision snapshot atomically, increment acquisition revision, then return 202 with its public acquisition. No network in the request. Duplicate calls using the current acquisition revision return the existing job without requeueing it; stale revisions return 409. Reserve each canonical v1 hash globally with a unique index, including unresolved/submitted jobs: another acquisition cannot silently take over that torrent. Job/private references never enter browser storage or diagnostics.
- SUB-002: Persist kind/version, acquisition/hash, queued/running/succeeded/needs-review state, due time, attempts, renewable lease token/expiry, whether add may have happened, and sanitized error. Four workers by default, existing bootstrap range 1–8. Claim queued jobs transactionally, one job per acquisition/hash; 60-second leases renewed every 15 seconds. All subsequent effects and database completion require the current unexpired token. Never reassign an expired running job within the live process: cancel/exit it; startup under the OS lock resets abandoned running jobs to queued for reconciliation, retaining add-attempt evidence. Stop workers before closing SQLite. No network inside SQL transactions.
- SUB-003: Workers use fresh cookie sessions, matching Origin/Referer, redirect refusal, stable qBittorrent 5.x/API 2.x checks and sanitized failures. Bound each HTTP attempt to two seconds and each job to 25 seconds plus one-second best-effort logout. Read-only JSON is limited to 64 KiB. Failures before add become review, with explicit retry rather than repeated authentication. Rate-limit failures persist a due time honoring Retry-After (1–3600 seconds), enforced on explicit retry. Local readiness remains independent of client health.
- SUB-004: Every job/retry begins by querying torrents/info with the exact hash and no category/tag filter. One exact hash with category `louro` and tag `louro-acquisition-<id>` confirms submitted; a different/missing owner, duplicate rows, malformed hashes or invalid responses require review without modifying that torrent. Never adopt, rename, retag, move or delete an existing foreign torrent. Do not treat an add response alone as proof. After add, query again; disappearance or failed visibility leaves uncertain. Reconciliation never issues add once add-attempt evidence is persisted, even when the client returns an empty list. Explicit Reconcile again is read-only for uncertain jobs; safely absent evidence is not proof that a previous add did not happen.
- SUB-005: Only the initial job or an explicit retry of a pre-add failure may add, after successful empty hash lookup. Ensure category `louro` exists by reading categories, creating only when absent and rereading after creation; do not edit existing category settings. Pass the captured download directory as savepath, autoTMM=false and the per-acquisition tag. Use the original private magnet or exact saved metainfo multipart bytes; never ask qBittorrent to fetch a provider URL. Persist add-attempt evidence before one add request. Unsupported/missing private payload becomes review. No automatic add retry, no tracker/media fetching by this application, no client preferences changes. qBittorrent may begin transfer after submission; paths must already match between the service and client.
- SUB-006: Recheck client and settings revisions at claim/before add and completion; a change pauses review and never sends saved credentials to a replacement endpoint. In-flight remote effects cannot be fenced by a local revision; retain add-attempt evidence and require review if configuration changes during an attempt. Existing jobs keep their original client revision and are not rebound automatically. Submitted/uncertain jobs retain hash ownership. Cancellation and identity preparation return 409 submission-exists once any job exists; this slice does not remove torrents or claim cancellation stopped a transfer.
- SUB-007: POST `.../{id}/reconcile` accepts exactly `{revision}`. Require a review job, unchanged client/settings revisions and elapsed cooldown; atomically queue it and increment acquisition revision. Pre-add jobs may add only after fresh reconciliation; jobs with add-attempt evidence are permanently reconciliation-only. Queued/running/submitted calls with current revision return the existing acquisition without duplicate work. Expose optional `submission` in acquisition reads/lists with state queued/running/submitted/uncertain/needs-review, clientRevision, attempts, errorCode (nullable), updatedAt. Raw responses, URLs, credentials and lease tokens stay private. Refresh reads work offline/restart.
- SUB-008: Additive schema 9 creates submission_jobs with foreign keys, unique acquisition/hash and indexed due work. Preserve schema-8 observations, private payloads, replay mappings, catalog/configuration/associations and credentials. Startup recovery and required-column readiness checks fail closed. Old binaries reject schema 9; rollback restores a matching stopped-service schema-8 backup, never destructive Down. No new dependency/toolchain.
- SUB-009: Saved acquisitions offers Submit to qBittorrent for ready/unsubmitted records, with an accessible confirmation showing candidate and saved download directory/client URL. Read current client/settings before confirmation; send the displayed client and settings revisions. Clearly say transfer may start and paths must match. Cancel closes without queueing. History shows submission state and classified error, Refresh, and Retry submission/Reconcile again for review. Automatic refresh every two seconds only while a visible history page has queued/running jobs; no automatic submission/retry. Hide local cancellation after queueing. Localize English/pt-BR and preserve branding/navigation/theme/mobile behavior; the mock Downloads screen stays unchanged.

Submission errors retain global request protections: 422 validation-failed, 404 acquisition-not-found; 409 acquisition-changed/acquisition-state-conflict/submission-exists/submission-hash-conflict/download-client-changed/download-client-unconfigured/submission-configuration-changed/submission-cooldown; 503 storage-unavailable/not-ready. Revision replay requires reading current state; a lost queue response cannot create a second job. Provider errors become persisted review/uncertain codes, never raw API diagnostics.

Verify public APIs with real disposable SQLite/directories and HTTP simulators: queue without network, revision/hash exclusion, lost add response, misleading success, foreign ownership, absent/invalid lookup, pre-add failure/retry, cooldown, metainfo/magnet forwarding, category behavior, client/settings races, worker claim/renew/expiry fences, shutdown, restart recovery, migration failure/preservation/older-reader refusal. Browser confirmation/history/retry and Windows/Linux checks are required. Live credentials are optional; client transfer permission and path mapping remain deployment validation.

Protocol checked against [official qBittorrent 5.x API](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-%28qBittorrent-5.0%29) on 2026-11-06. Louro category/tag spelling follows ADR-0003. Conservative no-resubmission after uncertain add is an application policy, not an exactly-once guarantee from the client.

## Ticket 04: download tracking and import evidence

This slice observes transfers; it does not import, play, move, delete or modify media, start/stop torrents or submit again. The existing Downloads navigation becomes a real service-backed screen; prototype movie controls cannot create real downloads.

- POL-001: Atomically create one download task for each confirmed successful submission, keyed by acquisition ID and linked to its immutable client/hash/directory/settings evidence. Schema-9 submitted jobs are backfilled for an initial check; unconfirmed jobs have no task. New task state pending, revision 1, unknown metrics/timestamps and no handoff. Download tasks and state/error/handoff transitions persist locally. Poll results do not change submission authorization or release its hash reservation.
- POL-002: Share the existing four-worker pool (bootstrap range 1–8) across submission and poll steps with fair rotation. Persist poll kind/version, attempts, queued/running/idle, due time and 60-second lease renewed every 15 seconds. Claim only due queued work transactionally; one active poll per task and no submission/poll overlap. No worker waits between polls: schedule active transfers for 15 seconds after completion of the check. Abandoned running polls requeue on startup under the instance lock, preserving history/last observations; no in-process lease takeover. Old tokens/expired leases cannot renew or finish. Shutdown cancels and joins both kinds before closing storage.
- POL-003: Each poll is read-only apart from authentication/logout: fresh qBittorrent session/version checks, exact hash lookup without category/tag filters, category louro and only its matching louro-acquisition tag. Require one matching row; missing torrent, changed ownership or conflicting tags pause review without adoption or mutation. Recheck saved client/settings revision before authentication, after authentication and at commit; never rebind old work to new settings or endpoints. Use two-second requests, 25-second operation plus one-second cleanup, 64 KiB info and 1 MiB files responses. Never expose raw responses, private provider references, cookies or tracker URLs.
- POL-004: Parse required state/progress/size/amount_left/dlspeed as typed bounded data: finite progress 0–1, JSON-safe nonnegative integer byte counts/speed, remaining no larger than selected size. Public metrics stay unknown before first success and retain last observed values on a failed check with a separate error/time. Known downloading/metadata/stalled/forced/checking/allocation/moving states remain downloading; pausedDL/stoppedDL become paused, queuedDL becomes queued. Stable upload states uploading/stalledUP/queuedUP/forcedUP/pausedUP/stoppedUP can be completed only with positive size, progress exactly 1, amount_left 0 and positive completion_on within the checked time plus five minutes. Checking/moving never produce handoff. Unknown/new states pause review; error/missingFiles become failed. No inferred success from 100% alone.
- POL-005: Completion reads torrents/files then rereads exact info in the same session, requiring unchanged ownership, completion, size, timestamp, save_path and content_path before committing file evidence. Save path must lexically equal the captured local download root, content path must be inside it. Validate every file's unique bounded index, normalized safe relative path (UTF-8, at most 4096 bytes/64 components, no traversal/absolute/drive/UNC, controls, Windows-invalid/reserved/trailing-dot/space components), positive JSON-safe size for selected files, known priority 0/1/6/7 and progress 0–1. At most 10000 entries; case-insensitive duplicate paths are ambiguous. Selected files must be complete and their total size must equal the reported selected size. Candidate extensions initially match inventory: mkv/mp4/avi/mov/m4v/ts. Exactly one selected complete candidate yields a version-1 handoff awaiting-validation with index/relativePath/sizeBytes; zero or multiple candidates or incomplete selected files yield a completed transfer with handoff needs-review and a fixed reason. Sample-like names are not automatically discarded. Unsafe/inconsistent metadata pauses task review with no handoff. No local path is opened or ffprobe run by polling. Lexical evidence is not proof of filesystem safety, video validity or movie identity.
- POL-006: Transient timeout/unavailable/rate-limit checks become unavailable and schedule max(15, Retry-After) seconds later (Retry-After 1–3600). Retain last successful metrics; clear current handoff/completion evidence. Auth/version/malformed responses, missing/foreign torrent, invalid paths and changed configuration pause needs-review; client error/missingFiles pause failed. Completed checks (including ambiguous handoff) become idle. An explicit Check download can queue an idle task with current revision; it clears current handoff/completedAt and sets pending before retrieval. It never bypasses a queued cooldown or duplicates running work. Revision-safe reads/retries recover lost responses. A future importer must re-observe ownership/completion and validate the actual local file, size, video stream and movie identity before effects; this snapshot alone never authorizes import.
- POL-007: Public GET /api/v1/downloads supports limit 1–50 (default25), offset 0–10000 and optional movieId. GET /api/v1/downloads/{acquisitionId} returns download plus newest 50 transition events and eventTotal. Task includes title/release identity, immutable hash/client revision, current revision/state/pollState/nextCheckAt, nullable metrics/clientState/errorCode/lastCheckedAt/lastObservedAt/completedAt/handoff and updatedAt. Events record state/code/progress/handoffState/time only when state/error/handoff changes, not every identical progress poll. POST .../{id}/check requires exactly positive revision, normal mutation protections and setup; returns 202 for queued/existing work, 404 download-not-found, 409 download-changed/download-check-cooldown/download-client-changed/submission-configuration-changed, 422 validation-failed, 503 storage-unavailable/not-ready. Reads are local and offline; API calls do not perform network work.
- POL-008: Additive migration 10 creates tasks/events, backfills only confirmed submissions and validates required schema. Preserve all schema-9 configuration, metadata, file associations, private metainfo, request mappings, jobs, hash reservations and credentials. Migration/recovery failure aborts startup; older binaries reject 10. Rollback restores a matching stopped-service schema-9 backup, never Down. Keep transactions short/local and atomically commit task/result/event; no new dependency/toolchain. History is append-only in this slice; retention maintenance belongs to operations.
- POL-009: Downloads shows real empty/loading/error/list/detail states, progress/bytes/speed, last check, terminal/review reasons and bounded transition history. Refresh reads local state; Check download only schedules observation and says it never restarts a transfer. Visible active tasks refresh every two seconds, with pagination, stale-response cancellation and no localStorage persistence of operational data. Completed tasks distinguish awaiting file validation from ambiguous handoff and never show a working Import button. Link submitted acquisitions to their download detail. Replace the prototype Downloads queue and remove Add to mock downloads; other prototype screens/playback remain mocked. Use the shared navigation/header/branding, both themes and en-US/pt-BR with accessible progress and mobile layout.

Poll/reference-state mapping and conservative evidence limits are Lôro policies checked against [qBittorrent 5.x API](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-%28qBittorrent-5.0%29) on 2026-11-06. Completion is a client report until the later import validators establish local evidence.

Verification: public API + real temporary SQLite/directories and external HTTP simulators, due scheduling/no worker hold, exclusion/renewal/expiry/restart, submission handoff/backfill/rollback, progress/paused/failure/outage/cooldown, foreign/missing torrent, malformed/bounded fields, completion recheck races, single/multiple/incomplete/unsafe files, configuration changes, event atomicity, shutdown, Windows and Linux container checks; browser live Downloads navigation/confirmation independence, progress/history/retry, localization/mobile. No live credentials required for development.
