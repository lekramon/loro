# Movie catalog and metadata

Label: ready-for-agent
State: done

## Scope and sequence

Ticket 01 implements backend TMDB search, durable duplicate-safe registration, offline catalog browsing, local artwork caching and attribution. Ticket 02 subsequently specifies existing-file scanning and explicit association/review. The interface is being designed independently in v0; the mock UI remains separate from actual catalog records.

## Ticket 01 contract

- Search TMDB API v3 by query, optional year, page and interface metadata language (`en-US` or `pt-BR`, default en-US). Normalize stable TMDB identity, title/original title, original language, release year, overview, genres, runtime and locally served poster/backdrop URLs. Unknown year/runtime remain null, missing text/artwork stays empty; no invented quality/audio availability.
- Public operations: GET `/api/v1/metadata/status`, GET `/api/v1/metadata/search`, POST/GET `/api/v1/catalog/movies`, GET `/api/v1/catalog/movies/{id}`, GET `/api/v1/metadata/images/{size}/{filename}`, GET `/api/v1/about`. Wire schemas are in [openapi.json](openapi.json). Existing Host/Origin/mutation protections and 64 KiB body limits apply. Catalog mutations require completed onboarding. Reading an empty catalog does not require onboarding.
- Registration body contains only positive `tmdbId` and optional `language`. Fetch authoritative movie details rather than trusting browser-supplied metadata. A unique TMDB database constraint protects identity; first registration returns 201, repeat returns 200 and the same internal ID without requiring provider access. A registered title has `hasMedia=false` until later file associations exist; this does not prove that no file exists on disk.
- List catalog through bounded `limit` (1–100, default 50), `offset` (0–1000000) and literal title filter `q` (at most 200 characters); deterministic title/ID ordering. Individual lookup uses internal ID. Catalog reads never call TMDB and survive provider failure, missing credentials and restart.
- Cache normalized metadata search/detail responses in SQLite for 24 hours, at most 500 cached queries. Fresh responses are served without network. Expired cached responses may be returned as explicitly stale when provider access fails; never turn a provider error into an empty successful search. Registered metadata remains durable and is not evicted with query caches. Registration may use a cached authoritative detail response.
- Only artwork paths observed in provider metadata may be fetched, using fixed TMDB CDN sizes w342/w780 and a fixed HTTPS origin. Return local API URLs. Fetch lazily with a maximum 8 MiB image, JPEG/PNG validation and bounded pixel dimensions. Store verified images atomically under private application cache directories; cap artwork cache at 128 MiB by evicting oldest managed files. Cached images remain available offline until eviction. Reject traversal, unknown sizes, unobserved image paths, redirects and non-image responses. Never forward the API token to the image CDN.
- External requests: at most four concurrent HTTP operations, two-second per-attempt timeout and an overall request budget below the server write deadline. Retry transient network errors and 5xx at most three times after the first attempt, with bounded exponential backoff. Never retry authentication, malformed responses, 404 or 429 blindly. Honor bounded Retry-After via a process-local provider cooldown.
- Classify missing credentials (503), authentication rejection (503), unavailable provider (503), timeout (504), rate limit (429 with Retry-After), missing provider movie (404), malformed provider responses (502), storage unavailability (503), invalid input (422), malformed JSON (400), missing setup (409), unknown catalog ID (404) and unexpected persistence failure (500). Public errors/logs never include credentials, provider response bodies or full integration URLs.
- Runtime credential hook: `--tmdb-token-file` overrides `PIRATARR_TMDB_TOKEN_FILE`. Without a file, use an optional application credential embedded by maintainer release packaging. Source-only builds have no credential by default. Private files are read afresh for new provider calls, enabling rotation; absent/unreadable/invalid credentials disable metadata queries without preventing startup, readiness or offline browsing. Status reports configured presence, not successful authentication, and exposes no credential/path.
- Release hook: BuildKit secret `tmdb_token` populates an otherwise empty embedded backend credential during compilation. Its value never appears in command arguments, logs, frontend assets or tracked source. A non-secret `TMDB_BUILD_REVISION` build argument invalidates secret-insensitive build cache for provisioning/rotation. Bundled application credentials are recoverable from a distributed binary, as accepted in ADR-0001. Test this hook with a dummy credential; use the privately provisioned token only in an explicitly opted-in live smoke check.
- Provide an About/Credits screen with an approved locally bundled TMDB logo and the exact required notice. Metadata/catalog responses link to the attribution resource. No redesign of the v0/mock UI is part of this ticket.

## Existing-file scan sequence

Ticket 02 prepares this contract; ticket 03 implements inventory and a real Files tab inside Library; ticket 04 will specify and implement explicit movie association/review before acquisition work.

### Inventory slice (ticket 03)

- SCN-001: POST `/api/v1/library/scan` with exactly an empty JSON object scans only the saved movie directory. Setup is required. Manual synchronous scan, one active scan per process; concurrent request returns 409 scan-in-progress. No timers, watchers or durable workers in this slice. Bound work to 100,000 directory entries, 10,000 supported files, depth 64 and a 10-second application budget. Exceeding limits returns 422 scan-limit; cancellation/timeout 503 scan-unavailable. No partial publication.
- SCN-002: Walk with an OS-rooted directory handle, bounded directory batches and context checks. Ignore symlinks (including internal targets), special files and unsupported extensions; reject symlinked/redirected configured roots and application-data overlap. Recognize MKV, MP4, AVI, MOV, M4V and TS case-insensitively, independently of acquisition preferences. Record size (including zero) and UTC modification time; extension does not prove video validity or movie identity. Do not read video contents or contact metadata providers. Root/read/stat errors abort and preserve prior inventory. Files changing during enumeration abort or are reconciled by the next scan; this is an observation, not a verified media association.
- SCN-003: Publish all observations and last-success metadata in one SQLite transaction, checking the saved settings revision/root again inside that transaction. Revision changes return 409 settings-changed. File identity is canonical root plus relative path (case-folded keys on Windows), not filename/title or checksum. Repeated scans reuse IDs; update attributes in place. Hardlinks at different paths remain separate entries. Mark unseen entries missing only after a fully successful scan of that same root; never delete history/media. Reappearing paths recover their IDs. Root changes retain the old root's records; API/UI list only the current configured root.
- SCN-004: GET `/api/v1/library/files?limit=50&offset=0&status=all` returns one consistent paginated snapshot. Limit 1–100, offset 0–1000000; status all/present/missing; reject duplicate/unknown query fields. Stable relative-path/id ordering. Include current root, entries, total and last successful scan summary (null before first success). Inventory survives process restart/provider outage. New media inventory does not change catalog hasMedia until explicitly associated/validated by the next slice.
- SCN-005: A failed write, crash, interrupted request, missing root or settings change never partially marks files missing. Startup does not resume an interrupted synchronous scan; the last committed inventory remains, and users may repeat safely. An uncertain response is reconciled by reading the snapshot or rescanning. Client disconnect near commit may leave a fully committed result, never partial state.
- SCN-006: Additive Goose migration 4 adds inventory and scan summary tables, without altering settings/catalog records. Current binary accepts v3 and migrates; old binaries refuse v4. Rollback uses the pre-upgrade stopped-service data copy; do not automatically run Down or destroy scan history. Migration failure aborts startup. Readiness checks new tables. Validate preservation on Windows and non-root Linux.
- SCN-007: Add Files beneath Library with Scan folder, loading/empty/error, last-success summary, present/missing labels and bounded pagination. Requires setup and links to settings for missing configuration. Explicitly describe files as unverified inventory, distinct from mock Movies and actual metadata search. Keep the unified header/sidebar and en-US/pt-BR. No physical file mutations.

[Inventory API contract](library-openapi.json) is authoritative. Errors are sanitized: 400 malformed JSON, 403 Host/Origin/header, 413 body too large, 415 non-JSON, 422 invalid request/scan limits, 409 setup-required/scan-in-progress/settings-changed, 503 storage-unavailable/scan-unavailable/not-ready. Unknown methods 405. Root and relative paths appear only in intentional inventory/settings responses, not diagnostic error text.

### Association/review boundary (ticket 04)

No filename-based automatic identity assignment is authorized by inventory. Next slice will offer title/year guesses as suggestions, require explicit selection of a registered catalog movie, validate file containment/current identity plus ffprobe video detection, and persist association or ignore state. Ambiguous/unknown names remain unassociated; technical validity alone does not prove identity. Ignore is reversible and survives rescans; changing an observed file invalidates prior verification. Association must not rename/move/delete files. Its wire/recovery contracts must be published before implementation. This future work remains open; scan completion is not catalog completion.


## Explicit association and review (ticket 04)

- ASC-001: Inventory adds revision, reviewState (pending/associated/ignored), nullable movieId/verifiedAt, movieTitle and filename-derived suggestedTitle/suggestedYear. Guesses remove the extension, dots/underscores and a bounded year suffix; they never auto-select identity. Unknown year is null. Primary filename can be replaced by the parent folder for generic filenames. Ambiguity remains pending until explicit choice.
- ASC-002: POST `/api/v1/library/files/{id}/review` accepts exactly revision (positive integer), action (associate/ignore/reopen), and only for associate a registered internal movieId plus confirmIdentity:true. Returns the updated entry. 404 unknown file/current-root mismatch/movie; 409 stale revision/settings change/missing-or-changed file/ignored association/reopen non-ignored/concurrent library operation; 422 malformed field values or invalid/no-video/zero-size file; 503 missing ffprobe/storage; 504 probe timeout. Existing JSON/Host/Origin/header/body protections apply. API details are in library-openapi.json.
- ASC-003: Associate opens only a nonzero regular current file under the configured OS-rooted folder, rejects symlink components, compares size/mtime to the observed row and verifies opened handle identity before/after probe. Run ffprobe on the opened handle as stdin using pipe:0 and pipe-only protocol whitelist, bounded JSON output (64 KiB) and an eight-second timeout within the API budget. Require a video stream. Never use browser paths, shell strings, URLs, stdout/stderr diagnostic payloads or external references. Missing executable produces a clear error; readiness/offline catalog remain available.
- ASC-004: Probe/identity confirmation occurs outside SQL. Transaction rechecks settings root/revision, file revision/presence and movie existence before updating reviewState/movieId/verifiedAt and incrementing file revision. No media mutation. Each process permits one scan/review operation at a time. A crash before commit leaves the prior state; after commit a lost response is reconciled by reading inventory (stale retry returns 409). No background resumption required.
- ASC-005: Ignore clears any association, persists ignored state and increments revision. Reopen only ignored entries back to pending. Ignore survives rescans and changed/missing files. Each successful scan increments existing observation revisions to fence stale review forms; missing or changed-size/mtime associations become pending and lose movieId/verifiedAt atomically. Unchanged verified associations survive repeated scans. Reappearing files require verification again after being observed missing. Catalog hasMedia derives from present associated records in the current configured root; it reflects last observations until rescanning, not continuous monitoring. Changing roots retains historical records but does not advertise old-root media as current.
- ASC-006: Migration 5 adds review columns without deleting inventory/catalog/settings. Version 4 data migrates to pending, older binaries refuse 5; rollback uses matching pre-upgrade stopped-service backup. Fail migration before accepting requests. Mixed binaries are excluded by the existing instance lock. No destructive Down runs.
- ASC-007: Files screen displays state/title/suggestion, offers Associate, Ignore and Reopen, and an accessible review dialog. Search existing catalog or TMDB explicitly; choosing a TMDB result registers it through the existing backend, then requires identity confirmation before probing/linking. Show classified localized errors; cancel has no association side effect (explicit metadata registration may already exist). No original files modified. Missing files cannot be associated. Real Movies browsing remains a separate UI ticket; this step changes real catalog hasMedia/API and Files review only.

Technical validity does not prove movie identity. File observation uses size/mtime and handle identity during verification, not a persistent content checksum; undetectable same-size/same-mtime replacement between scans is outside continuous integrity monitoring. Existing-file association does not require download-client completion; that prerequisite applies to later downloaded-file imports.
